# 조립 제조 ERP — 문서 기준과 상세 설계

> 2026-09-12 보존한 v1 구현 기준. 아래 실행·검증 결과는 수행 시점의 역사 기록이며 현재 production 완료를 의미하지 않는다. 새 목표는 [SSOT v2](SSOT.md)를 따른다. 기존 코드·DB·검증 결과를 설명하기 위해 보존한다.

문서 버전: 0.7  
작성일: 2026-09-11  
상태: MVP 설계 기준 / 구현 진행 중. 실제 구현·검증 상태는 [PROGRESS](PROGRESS.md)를 따른다.

## 1. 문서의 역할

먼저 [PRD](PRD-V1.md)를 읽는다. 제품 목표·범위·핵심 업무 정책·제품 인수 조건은 PRD가 기준이다.
이 문서는 PRD를 구현하기 위한 데이터·API·트랜잭션·연결과 기술 검증의 상세 설계를 담당한다.
SSOT는 한 파일에 모든 내용을 모으는 대신, 각 항목에 하나의 기준 문서를 지정하는 원칙으로 적용한다.

| 항목 | 기준 문서 |
| --- | --- |
| 목표·사용자·범위·업무 정책·제품 인수 조건 | [PRD](PRD-V1.md) |
| 입력 제한·데이터·API·트랜잭션·환경·기술 검증 | 이 문서 |
| 기술 선택의 배경·대안·결과 | [ADR 목록](adr/README.md) |

아래 업무 설명은 PRD 정책을 구체화한 것이다. 제품 요구와 충돌할 경우 PRD를 기준으로 설계를 수정하며, 제품 변경이 필요하면 PRD부터 변경한다.

- **사용자 확정 사항:** Go Fiber, SvelteKit, Neon, sqlc + pgx, 모노레포, 모듈형 모놀리스, 조립 제조, 최소 MVP, 로그인 없는 로컬 데모, 부분 생산·불량 지원.
- **사용자 확정 업무 규칙:** 계획은 양품+불량 처리 목표이며, 실적 등록 시 양품+불량의 자재를 차감하고 양품만 입고한다.
- **설계 기본값:** 별도 사용자 지정이 없는 API 형식, 수량 상한, 상태명, 테이블 구성 등은 이 문서가 정한 MVP 기본값이다. 사용자 요구가 바뀌면 구현 전에 함께 수정한다.
- 최초 문서 작성 요청 이후 2026-09-11 후속 요청으로 코드 구현을 시작했다. 로컬 PostgreSQL 구현·검증 후 사용자가 별도로 승인한 `assembly-erp` Neon 프로젝트를 생성했다. 이 문장과 연결된 결과는 당시 작업의 역사이며 현재 production 배포·운영 완료를 뜻하지 않는다.
- 2026-09-12 사용자가 reverse-proxy Basic Auth를 거절해 이전 보호 요구를 대체했다. v1 데모는 익명 읽기·쓰기가 가능하며 데이터 격리나 읽기 전용 보호를 제공한다는 뜻이 아니다. v2 앱 계정·세션·서버 역할 권한 요구는 별도로 유지한다.
- 후속 OpenAPI 문서는 본 문서의 계약을 구체화한다. 불일치가 발견되면 문서와 구현을 같은 작업에서 일치시킨다.

## 2. 목표와 범위

목표와 성공 기준은 [PRD 4절](PRD-V1.md#4-목표와-성공-기준), 기능과 제외 범위는 [PRD 5절](PRD-V1.md#5-mvp-요구사항)을 따른다.
이 문서의 테이블·API·화면 설계로 제품 범위를 추가하지 않는다. MSA, 메시지 브로커, 캐시는 현재 기술 구성에 포함하지 않는다.

## 3. 용어와 수량 규칙

| 용어 | 정의 |
| --- | --- |
| 부품 | 생산 과정에서 소비되는 품목 |
| 완제품 | BOM에 따라 생산해 재고에 추가하는 품목 |
| BOM | 완제품 1개당 필요한 부품과 정수 수량 |
| 계획 수량 | 양품과 불량을 합친 처리 목표 |
| 처리 수량 | 누적 양품 + 누적 불량 |
| 잔여 수량 | 계획 수량 - 처리 수량 |
| 현재고 | 해당 품목의 입고와 출고 증감을 누적한 값 |
| 실적 | 한 번에 처리한 양품·불량 수량 기록 |

- 재고 위치는 하나로 간주한다. 창고 테이블은 만들지 않는다.
- 품목 단위는 표시 정보이며, 소수와 단위 환산은 지원하지 않는다.
- 입고 수량, 계획 수량, BOM 소요량은 1~1,000,000의 정수로 제한한다.
- 실적의 양품·불량은 각각 0~1,000,000의 정수이며 합계는 1 이상, 잔여 수량 이하여야 한다.
- 수량과 계산은 Go int64 / PostgreSQL BIGINT를 사용한다. API는 JSON 정수로 표현한다.
- 현재고 상한은 1,000,000,000,000으로 둔다. 연산 후 상한을 넘으면 요청 전체를 거절한다.
- 품목 코드는 공백을 제거한 대문자로 정규화하며 `[A-Z0-9_-]` 1~40자로 제한한다. 코드 중복은 허용하지 않는다.
- 이름은 공백 제거 후 1~100자, 단위는 1~20자, 선택 메모는 최대 500자로 제한한다.
- 시간은 서버가 UTC로 기록하며 API는 RFC 3339 형식으로 반환한다. 화면에서는 Asia/Seoul로 표시한다.

## 4. 핵심 업무 흐름

1. 부품과 완제품을 등록한다. 등록 시 수량 0의 재고 행을 함께 만든다.
2. 부품을 수동 입고한다. 입고 기록과 재고 증가 이력을 함께 남긴다.
3. 완제품의 BOM을 등록한다. 최소 한 개의 부품이 필요하며 중복 부품은 거절한다.
4. 완제품과 계획 수량으로 생산 지시를 만든다. 이 시점의 BOM 전체를 지시에 복사한다.
5. 실적을 등록할 때 잔여 수량과 부품 재고를 검증한다.
6. `이번 처리 수량 = 양품 + 불량`으로 계산해 각 BOM 부품을 차감한다.
7. 양품 수량만 완제품 재고에 추가하고 실적과 재고 이력을 저장한다.
8. 누적 처리 수량에 따라 상태를 계산한다.

### 상태

| API 상태 | 화면 | 조건 |
| --- | --- | --- |
| pending | 대기 | 누적 처리 수량 = 0 |
| in_progress | 진행 중 | 0 < 누적 처리 수량 < 계획 수량 |
| completed | 완료 | 누적 처리 수량 = 계획 수량 |

상태는 누적 수량에서 계산하며 임의 상태 변경 API는 제공하지 않는다.
지시는 재고 부족 상태에서도 만들 수 있다. 실제 소비 가능 여부는 실적 등록 시 판단한다.
완료된 지시에 새로운 실적을 등록할 수 없지만, 이미 성공한 동일 요청의 재전송은 기존 결과를 반환한다.

### 예시

키보드 1개의 BOM이 케이스 1개, 스위치 80개이고 계획 수량이 10개인 경우:

| 등록 | 양품 | 불량 | 케이스 차감 | 스위치 차감 | 완제품 증가 | 잔여 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1차 | 4 | 1 | 5 | 400 | 4 | 5 |
| 2차 | 3 | 2 | 5 | 400 | 3 | 0 |

최종 양품은 7개, 불량은 3개이며 지시는 완료다. 부족한 양품 3개가 필요하면 새 지시를 만든다.
불량은 자재를 전량 소비한 것으로 보고 불량 재고나 회수 재고를 별도로 만들지 않는다.

## 5. 트랜잭션과 정합성

### 실적 등록

하나의 pgx 트랜잭션에서 다음을 처리한다.

1. 요청 식별자 중복 여부를 판정한다.
2. 생산 지시 행을 `FOR UPDATE`로 잠근다.
3. 지시와 복사된 BOM을 읽고 잔여 수량을 검증한다.
4. 부품 및 완제품 재고 행을 품목 ID 오름차순으로 잠근다.
5. 각 자재 부족과 완제품 현재고 상한을 검증한다.
6. 실적, 지시의 누적 양품·불량, 재고 잔액, 재고 변동 이력을 갱신한다.
7. 요청 식별자와 성공 결과를 함께 확정하고 커밋한다.

중간 오류가 있으면 전부 롤백한다. sqlc 쿼리는 반드시 같은 트랜잭션에 바인딩해서 사용한다.
모든 재고 변경 경로는 같은 품목 ID 잠금 순서를 따른다.
격리 수준은 READ COMMITTED를 기본값으로 하고, 행 잠금·고유 제약·수량 제약으로 경쟁 요청을 제어한다.
교착이나 잠금 시간 초과는 트랜잭션을 롤백하고 재시도 가능한 오류로 반환한다.

### 중복 요청

- 입고, 생산 지시 생성, 실적 등록에 `Idempotency-Key` UUID 헤더를 필수로 사용한다.
- 요청 키는 작업 종류와 함께 고유하게 저장한다. 정규화한 입력의 해시와 생성된 리소스 ID를 기록한다.
- 동일 키·동일 입력은 기존 리소스를 반환한다. 같은 키·다른 입력은 HTTP 409다.
- 요청 키 확보와 업무 쓰기는 같은 트랜잭션에서 처리한다. 실패한 요청은 키를 확정하지 않는다.
- 동시에 같은 키가 들어와도 고유 제약으로 하나만 성공시킨다. 중복 판정 후 기존 결과를 읽는다.
- MVP 동안 성공한 키를 만료시키지 않는다. 데모 초기화 시 함께 제거한다.
- 화면은 제출 중 버튼을 비활성화하고, 응답이 불명확한 재전송에는 기존 키를 사용한다.

### 추가 불변 조건

- 현재고는 음수가 될 수 없고, 재고 잔액은 변동 이력의 합계와 일치해야 한다.
- 누적 양품·불량은 실적 합계와 일치하고 합계가 계획을 넘을 수 없다.
- 양품 0인 실적에서는 완제품의 0수량 변동 이력을 만들지 않는다.
- BOM 교체는 한 트랜잭션으로 수행한다. 지시 생성과 BOM 교체는 BOM 헤더를 잠가 복사 도중 구성이 섞이지 않도록 한다.
- 연관 레코드의 고아화를 외래 키로 막고, 수량 범위는 가능한 항목에 CHECK 제약을 적용한다.

## 6. 논리 데이터 모델

UUID를 리소스 식별자로 사용한다. 아래는 책임과 관계의 기준이며 실제 DDL은 구현 단계에서 작성한다.

| 데이터 | 주요 필드 / 역할 |
| --- | --- |
| items | id, code(고유), name, kind(component/finished_good), unit, created_at |
| boms | id, finished_item_id(고유), updated_at — 완제품별 현재 BOM 헤더 |
| bom_lines | bom_id, component_item_id, quantity_per_unit — 부품 조합 고유 |
| inventory_balances | item_id(PK/FK), quantity, updated_at — 품목당 한 행 |
| stock_receipts | id, item_id, quantity, note, created_at — 한 요청에 한 부품 입고 |
| production_orders | id, finished_item_id, planned_quantity, good_quantity, defective_quantity, created_at |
| production_order_materials | order_id, component_item_id, quantity_per_unit — 지시 생성 시 BOM 복사 |
| production_results | id, order_id, good_quantity, defective_quantity, note, created_at |
| stock_movements | id, item_id, delta, movement_type, receipt_id 또는 result_id, created_at |
| idempotency_requests | operation, key, request_hash, resource_id, created_at — 작업·키 조합 고유 |

재고 변동 종류는 `manual_receipt`, `production_consumption`, `production_receipt`다.
수동 입고는 receipt_id만, 생산 변동은 result_id만 갖도록 제약한다.
재고 이력은 수정하지 않는 기록이며, 잔액 갱신과 항상 같은 트랜잭션에 저장한다.
생산 지시 상태와 잔여 수량은 누적 수량으로 계산해 응답한다.

## 7. API 계약

REST JSON API의 기본 경로는 `/api/v1`이다. v1 애플리케이션 자체 인증은 없다. 기본 실행은 loopback 접근만 허용하며, production은 loopback에 바인딩된 API 앞의 Caddy 역프록시와 정확히 지정한 공개 Host를 사용한다. 사용자 결정으로 Caddy Basic Auth를 사용하지 않으므로 익명 호출자는 v1 데모 데이터를 읽고 쓸 수 있다. Host·Origin 검사는 사용자 인증이나 데이터 격리를 대신하지 않는다.

| 메서드 / 경로 | 입력 또는 동작 |
| --- | --- |
| POST /items | code, name, kind, unit |
| GET /items | 품목 목록, kind 필터와 q(코드·이름 검색) |
| GET /items/{id} | 품목 상세 |
| PUT /items/{id}/bom | components: [{item_id, quantity_per_unit}] — 전체 교체 |
| GET /items/{id}/bom | 현재 BOM 조회 |
| POST /stock-receipts | item_id, quantity, note? / Idempotency-Key 필수 |
| GET /stock-receipts/{id} | 입고 상세 |
| GET /inventory | 현재고 목록, kind와 q 필터 |
| GET /stock-movements | 재고 이력, item_id 필터 |
| POST /production-orders | finished_item_id, planned_quantity / Idempotency-Key 필수 |
| GET /production-orders | 지시 목록, status 필터 |
| GET /production-orders/{id} | 계획·누적·잔여·상태와 복사된 BOM |
| POST /production-orders/{id}/results | good_quantity, defective_quantity, note? / Idempotency-Key 필수 |
| GET /production-orders/{id}/results | 해당 지시의 실적 목록 |
| GET /production-results/{id} | 실적 상세 |

- 생성 성공은 201, 조회·BOM 교체·중복 요청 재응답은 200을 사용한다.
- 단건 응답은 `{data: ...}`, 목록은 `{data: [...], pagination: {page, page_size, total}}` 형식이다.
- 목록은 page=1, page_size=20 기본값과 최대 100을 적용한다. 최신 생성 순·ID 순으로 정렬하며 현재고 목록은 품목 코드 순으로 정렬한다.
- 실패는 `{error: {code, message, details?}}` 형식으로 반환하고 DB 내부 오류는 노출하지 않는다.
- 400: 입력·헤더 오류, 404: 대상 없음, 409: 재고 부족·계획 초과·완료 지시·중복 코드·요청 키 충돌·재고 상한, 503: 일시적 DB 연결/잠금 실패, 500: 예상하지 못한 오류.
- 자재 부족 응답 details에는 부족한 품목 ID, 필요 수량, 현재 수량을 포함한다.
- BOM 없는 완제품에 생산 지시를 생성하면 409로 거절한다. 잘못된 품목 종류를 사용하는 요청은 400이다.
- 생성 API의 재시도는 기존 Idempotency-Key로 수행한다. 업무 충돌은 입력이나 재고를 해결한 뒤 새 요청으로 제출한다.

## 8. 화면과 사용자 경험

| 화면 | 핵심 표시와 동작 |
| --- | --- |
| 품목 관리 | 종류·코드·이름·단위 목록, 신규 등록 |
| BOM 편집 | 완제품 선택, 부품 행 추가·제거, 소요량 입력, 전체 저장 |
| 재고 | 품목별 현재고, 부품 입고 폼, 품목별 이력 진입 |
| 재고 이력 | 일시, 품목, 변동 종류, 증감 수량, 연결 입고·실적 |
| 생산 지시 목록 | 완제품, 계획, 양품, 불량, 잔여, 상태, 생성일, 신규 지시 |
| 생산 지시 상세 | 복사된 BOM, 계획·집계, 실적 목록, 양품·불량 입력 |

- 한국어 데스크톱 업무 화면을 기본으로 한다. 로딩·빈 목록·조회 실패·저장 실패 상태를 제공한다.
- 생산 실적 입력 시 예상 부품 소비량을 보여주되 최종 재고 판정은 서버가 한다.
- 성공 후 지시 집계와 재고를 재조회한다. 수량이 중요한 쓰기에 낙관적 갱신을 사용하지 않는다.
- 실패 시 입력을 유지하고 오류 원인을 표시한다. 완료된 지시의 실적 입력은 비활성화한다.

## 9. 기술 구조와 Neon 연결

### 저장소와 책임

- `apps/web`: SvelteKit + TypeScript 화면 및 API 호출.
- `apps/api`: Go Fiber 핸들러, 품목·재고·생산 서비스, sqlc 쿼리·생성 코드, Goose 마이그레이션.
- `contracts`: 후속 OpenAPI 계약.
- `docs`: 이 문서와 후속 설계 기록.

위 디렉터리를 기준으로 구현한다. 디렉터리·코드 작성과 실제 검증 완료를 구분해 PROGRESS에 기록한다.
백엔드는 하나의 Go 모듈·프로세스로 구성한다. 범용 저장소 추상화 대신 업무에 필요한 쿼리를 명시한다.
Fiber 타입은 HTTP 계층에 한정하고 서비스와 DB 호출에는 표준 context.Context를 전달한다.
sqlc 생성 모델을 API 응답으로 직접 노출하지 않는다. 생성 코드는 커밋하고 수동 수정하지 않는다.

### 연결과 환경

- 경로: SvelteKit → Fiber → sqlc + pgx → Neon PostgreSQL.
- `DATABASE_URL`: API의 Neon 연결 주소. 초기에는 직접 연결과 작은 pgxpool을 사용한다.
- `MIGRATION_DATABASE_URL`: Goose용 직접 연결 주소. 테스트는 로컬 PostgreSQL 주소로 대체한다.
- 접속 비밀값은 백엔드 환경 변수로만 전달하며 Git·문서·브라우저 번들·로그에 넣지 않는다.
- Neon 연결은 `sslmode=verify-full`로 서버 인증서를 검증한다.
- 초기 풀은 MaxConns=5, MinConns=0, 연결 타임아웃=15초를 기본으로 한다. DB 작업 컨텍스트에는 20초 제한을 둔다.
- 컴퓨트 재개 이후 요청과 연결 실패 복구를 검증한다. DB를 깨우기 위한 주기적 쿼리는 추가하지 않는다.
- 서버 인스턴스 증가 시 Neon 풀러 도입과 prepared statement 호환성을 별도 검증한다.
- 브라우저 요청은 같은 출처의 `/api`로 전달한다. 개발에서는 Vite proxy, production에서는 Caddy가 로컬 Fiber에 연결한다.
- production SvelteKit은 `adapter-node`를 사용하고 `127.0.0.1:3000`, Fiber는 `127.0.0.1:8080`에 바인딩한다. Rocky Linux Docker Compose는 host network를 사용하되 Caddy만 80/443을 공개한다.
- Caddy는 `erp.jisung.lol`의 TLS·보안 헤더·역프록시를 담당하며 사용자 결정에 따라 Basic Auth를 적용하거나 복원하지 않는다. v1 배포 확인은 Basic Auth 없는 화면·읽기 API 정상 응답을 기준으로 하며 익명 401을 요구하지 않는다.
- API Host 검사는 loopback을 기본 허용하고 `PUBLIC_APP_HOST`로 지정한 정확한 DNS 호스트 하나만 추가 허용한다. 쓰기 요청 Origin은 실제 Host와 동일해야 하며 cross-site 쓰기는 계속 거절한다.
- CI는 Neon 비밀값 없이 격리 로컬 PostgreSQL에서 기존 검증을 수행한다. main CI 성공 후 CD가 commit SHA Docker image를 GHCR에 올리고 SSH로 Rocky Linux에 배포한다.
- 배포 migration은 `up` one-shot으로 한 번만 실행하고 자동 seed/reset/down은 수행하지 않는다. DB 비밀값은 서버의 `.env.production`에만 둔다. Basic Auth 사용자·해시는 필수 환경 변수가 아니다.
- 로컬 테스트 DB는 Neon과 분리한다. 데모 초기화 명령은 명시적으로 지정한 전용 데모 DB에만 적용하며 서버 시작 시 자동 실행하지 않는다.

### 리소스와 버전

사용 가능한 리전을 조회한 뒤 한국 로컬 실행 환경과 가까운 싱가포르에 ERP 전용 PostgreSQL 17 프로젝트를 생성했다. 대상 메타데이터와 실제 연결 검증은 PROGRESS에서 관리한다. 기존 로컬 `.env`와 테스트 DB를 보존하고 명시적 Neon 명령만 Git에서 제외된 `.env.neon`을 사용한다.
정확한 라이브러리 버전과 실행 명령은 잠금 파일과 README에 고정했다.
무료 한도나 요금은 제품 규칙으로 고정하지 않으며 리소스 생성 시 최신 조건을 확인한다.

## 10. 검증과 완료 기준

제품 인수 기준은 PRD의 FR·BR·NFR과 10절을 따른다. 아래 표는 이를 검증하는 기술 시나리오다.

실제 PostgreSQL 통합 테스트를 사용해 SQL, 제약, 잠금과 롤백을 검증한다.

| 시나리오 | 합격 기준 |
| --- | --- |
| 기본 흐름 | 입고 → BOM → 지시 → 실적 → 재고 이력을 화면에서 완료 |
| 부분 생산 | 두 번 이상 실적으로 누적·잔여·상태가 정확히 변경 |
| 불량 | 양품 7·불량 3이면 자재 10개분 소비, 완제품 7개 입고 |
| 전량 불량 | 완제품 증가 없이 자재 소비와 지시 완료가 정확 |
| 입력 검증 | 음수·소수·전부 0·상한 초과·잘못된 종류를 거절 |
| 자재 부족 | 일부 자재만 충분해도 실적·모든 재고 변경을 롤백 |
| 계획 초과 | 잔여보다 큰 실적을 거절하며 데이터 변화 없음 |
| 동일 지시 경쟁 | 동시 실적이 계획을 넘지 않음 |
| 공통 자재 경쟁 | 서로 다른 지시가 같은 자재를 소비해도 음수 재고 없음 |
| 중복 제출 | 같은 키로 재요청·동시 요청해도 입고/지시/실적이 한 번만 생성 |
| 요청 키 충돌 | 같은 키의 다른 입력은 409 |
| 실패 주입 | 중간 쓰기 실패 시 실적·집계·잔액·이력·요청 키가 전부 롤백 |
| BOM 변경 | 기존 지시는 복사본 사용, 신규 지시는 최신 BOM 사용 |
| 이력 대조 | 품목별 이력 합계=현재고, 지시별 실적 합계=누적 수량 |
| Neon 확인 | TLS 연결·마이그레이션·생산 처리·유휴 후 첫 요청 성공 |

Go 테스트, sqlc 재생성 결과 일치, 프론트엔드 타입 검사와 빌드도 통과해야 한다.
브라우저에서 핵심 흐름과 오류 표시를 검증한다. 로컬 자동 테스트가 Neon 접속 정보에 의존해서는 안 된다.

## 11. 후속 구현 순서

구현 전에 PRD와 상세 설계의 정합성을 확인하고, [ADR 목록](adr/README.md)의 결정과 검증·재검토 조건을 따른다.

1. 기술 버전 고정, 모노레포·실행 환경·API 계약·스키마·예제 데이터 구성.
2. 품목·BOM·입고·재고를 화면과 API까지 연결.
3. 생산 지시·부분 실적·불량·트랜잭션·중복 요청 처리 구현.
4. 통합 테스트, 브라우저 검증, Neon 연결 검증.
5. README에 실제 실행법, ERD, 데모 절차, 설계 선택과 검증 결과를 추가.

후속 구현 요청에 따라 위 순서로 구현·검증한다. 아직 실행하지 못한 검증은 완료로 표시하지 않는다.
MVP 완료 판단은 [PRD 10절](PRD-V1.md#10-mvp-완료-조건)을 기준으로 하며, 이 문서 10절의 기술 검증으로 뒷받침한다.
