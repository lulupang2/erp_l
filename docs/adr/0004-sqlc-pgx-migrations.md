# ADR-0004: sqlc + pgx와 명시적인 SQL 마이그레이션

- 상태: v1 채택·구현 / v2에서도 유지; 버전별 검증은 [PROGRESS](../PROGRESS.md) 참조
- 기록일: 2026-09-11
- 출처: sqlc + pgx는 대안 비교 후 사용자 선택, Goose는 기존 설계 기본값
- 관련 요구사항: [PRD-V1](../PRD-V1.md) FR-06~07, NFR-01~03, NFR-06; v2 기술 스택 유지

## 배경

품목 CRUD와 함께 자재 차감, 실적 집계와 행 잠금을 구현해야 한다.
SQL을 검토할 수 있게 유지하면서 결과 매핑의 반복 코드를 줄이는 방향을 선택했다.

## 결정

ORM을 사용하지 않고 SQL을 작성한 뒤 sqlc로 Go 타입·쿼리 호출 코드를 생성한다.
pgx로 PostgreSQL 연결과 트랜잭션을 관리하고 트랜잭션에 바인딩된 sqlc 쿼리를 사용한다.
Goose의 SQL 마이그레이션을 DB 스키마 변경 이력으로 관리하며 앱 시작 시 자동 스키마 동기화를 하지 않는다.
생성 코드는 버전 관리하되 직접 수정하지 않는다. API 타입은 별도로 둔다.

## 검토한 대안

| 대안 | 판단 |
| --- | --- |
| GORM | CRUD 작성에 유용하고 트랜잭션·행 잠금도 가능하다. 이번에는 SQL을 직접 관리하는 접근을 선택했다. |
| pgx 직접 사용 | 생성 단계가 없지만 결과 매핑과 반복 코드를 직접 유지해야 한다. |
| 모델 기반 자동 스키마 변경 | 변경 SQL을 명시적으로 검토하고 환경별 적용 이력을 남기는 현재 방향과 맞지 않는다. |

Goose와 다른 마이그레이션 도구의 실증 비교는 하지 않았다. Goose는 기존 계획의 기본값이며 제품 필수 요건은 아니다.

## 결과와 단점

SQL과 호출 코드를 연결해 검토할 수 있고 반복 매핑을 줄인다.
SQL 작성·코드 생성·마이그레이션 도구를 함께 관리해야 하며 PostgreSQL 문법에 의존한다.
코드 생성 성공만으로 런타임 제약·동시성·쿼리 성능이 검증되지는 않는다.
기능 설명은 [sqlc 공식 소개](https://sqlc.dev/)와 [트랜잭션 문서](https://docs.sqlc.dev/en/latest/howto/transactions.html)를 따른다.

## 검증과 재검토 조건

실제 PostgreSQL에서 마이그레이션과 생성 쿼리를 실행하고 재생성 결과의 일치를 검사한다.
트랜잭션 도중 오류가 전체 쓰기를 롤백하는지 검증한다.
SQL 생성의 제약이나 동적 쿼리 요구가 개발을 실질적으로 막으면 해당 쿼리의 접근부터 재검토한다.
