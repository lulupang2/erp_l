# ADR-0005: Neon PostgreSQL과 독립된 로컬 테스트 DB

- 상태: 채택 / 실제 구현·검증 상태는 [PROGRESS](../PROGRESS.md) 참조
- 기록일: 2026-09-11
- 출처: Neon과 Supabase 비교 후 사용자 Neon 확정, 연결·테스트 구성은 기존 설계 기본값
- 관련 요구사항: PRD 3절·9절, NFR-05~06

## 배경

사용자는 서버리스 DB를 원하며 Neon과 Supabase 중 선택을 요청했다.
업무 API는 Go로 구현하고 현재 MVP는 인증·파일 저장·실시간 기능을 요구하지 않는다.
개발·데모 DB를 외부에서 운영하면서 자동 테스트는 네트워크와 클라우드 계정에 의존하지 않아야 한다.

## 결정

데모 DB는 Neon PostgreSQL을 사용하고 pgx로 연결한다.
초기 단일 Go 서버는 직접 연결과 작은 pgxpool을 사용하며 Goose도 직접 연결한다.
자격 증명은 백엔드 환경 변수로 관리하고 TLS를 적용한다. 상세 설정은 SSOT 9절을 따른다.
통합 테스트는 별도의 로컬 PostgreSQL에서 실행하고 Neon 연결·마이그레이션·생산 처리도 별도 확인한다.
테스트 PostgreSQL의 메이저 버전은 실제 Neon 프로젝트와 맞춘다.

## 검토한 대안

| 대안 | 판단 |
| --- | --- |
| Supabase | PostgreSQL 외 Auth·Storage·Realtime을 통합 제공한다. 현재 MVP에서 이 기능을 사용하지 않아 Neon을 선택했다. |
| 로컬 PostgreSQL만 사용 | 테스트에는 채택하지만 서버리스 DB를 사용하려는 사용자 선택을 충족하지 못한다. |
| 처음부터 Neon 풀러 사용 | 현재 단일 서버의 작은 풀을 먼저 사용하고 다중 인스턴스 연결 요구가 생기면 재검토한다. |

Supabase도 Go에서 DB로 직접 사용할 수 있다. 비교 결과는 이 프로젝트의 적합성 판단이며 일반적인 제품 우열이 아니다.
Neon의 유휴 컴퓨트 중단·재개는 [Scale to Zero 문서](https://neon.com/docs/introduction/scale-to-zero), Supabase 통합 구성은 [공식 아키텍처](https://supabase.com/docs/guides/getting-started/architecture)를 참고했다.

## 결과와 단점

자체 DB 서버 운영 부담을 줄이되 데모 실행에 인터넷과 Neon 가용성이 필요하다.
유휴 후 재개 지연과 연결 실패를 다뤄야 한다. 로컬 테스트만으로 클라우드 연결 동작까지 보장하지 않는다.
결정 작성 시점에는 프로젝트·리전·요금제를 선택·생성하지 않았다. 무료 한도나 비용은 설계의 고정 전제로 삼지 않는다.
서비스 정책, 네트워크 지연과 비용은 리소스 생성 시 다시 확인한다.

## 검증과 재검토 조건

유휴 후 첫 요청, 연결 실패 안내, 마이그레이션 적용과 핵심 생산 흐름을 확인한다.
인스턴스 증가·연결 한도 문제가 생기면 풀러와 드라이버 설정을 검증한다.
오프라인 데모 요구, 감당하기 어려운 비용·지연, 통합 백엔드 기능 요구가 생기면 공급자를 재검토한다.

## 구현 후속 기록

2026-09-11 별도 사용자 승인으로 ERP 전용 Neon 프로젝트를 생성했다. 직접 연결·작은 pgxpool·별도 로컬 테스트 DB 결정은 유지한다. 프로젝트 메타데이터, 실제 연결/브라우저/유휴 재개 결과와 미검증 범위는 PROGRESS와 NEON-CHECKLIST에서 관리한다. 기존 로컬 설정은 보존하며 명시적 Neon 명령만 별도 비밀값 프로필을 사용한다.
