# ADR-0001: 모노레포와 모듈형 모놀리스 채택

- 상태: v1 채택·구현 / v2에서도 구조 유지; 버전별 검증은 [PROGRESS](../PROGRESS.md) 참조
- 기록일: 2026-09-11
- 출처: 모노레포 + 모듈형 모놀리스 권고에 대한 사용자 선택
- 관련 요구사항: [PRD-V1](../PRD-V1.md) FR-01~07, NFR-02, NFR-06

## 배경

v1 최소 제조 ERP에서 화면·API·DB 변경을 함께 진행하며, 생산 실적과 재고는 함께 확정되어야 한다. v2에서는 [ADR-0009](0009-factory-production-flow.md)에 따라 생산·검사·입고의 전표별 원자성으로 나눈다.
독립 팀이나 서비스별 독립 배포 요구는 현재 없다. 우선 업무 흐름 전체를 완성하는 것이 목표다.
모노레포는 저장소 구성이고 모놀리스는 백엔드 실행 구조로, 별개의 결정 축이다.

## 결정

프론트엔드, Go API, API 명세와 문서를 한 저장소에서 관리한다.
백엔드는 품목·재고·생산 모듈로 나누되 하나의 Go 모듈·프로세스와 하나의 PostgreSQL DB로 구성한다.
모듈 경계는 코드 책임으로 유지하고, 생산 서비스가 필요한 재고 쿼리를 같은 트랜잭션에서 조정한다.
v1 저장소 배치는 [SSOT-V1 9절](../SSOT-V1.md#9-기술-구조와-neon-연결)에 기록되어 있으며 v2도 모노레포·모듈형 모놀리스를 유지한다.

## 검토한 대안

| 대안 | 선택하지 않은 이유 |
| --- | --- |
| 프론트·백엔드 별도 저장소 | API 변경을 저장소 간 조율해야 하며 현재 독립 소유권 요구가 없다. |
| 모노레포 안의 MSA | 저장소는 통합되지만 서비스 간 부분 실패와 데이터 일관성 비용은 남는다. |
| 경계 없는 단일 백엔드 | 초기에는 단순하지만 업무 책임과 테스트 범위를 구분하기 어렵다고 판단했다. |

## 결과와 단점

화면과 API를 같은 변경에서 관리하고 DB 트랜잭션으로 생산·재고를 연결한다.
대신 백엔드 전체가 함께 배포되며, 모듈별 독립 확장과 장애 격리는 제공하지 않는다.
폴더만 분리해도 결합도가 낮아지는 것은 아니므로 업무 로직을 핸들러에 모으거나 모듈 간 순환 의존을 만들지 않는다.

## 검증과 재검토 조건

전체 업무 흐름과 서비스 계층 테스트로 책임 분리가 유지되는지 확인한다.
특정 모듈의 독립 배포·격리·확장 필요가 실제로 생기면 분리를 재검토한다.
포트폴리오에서 서비스 수를 늘리기 위해 자동으로 MSA로 전환하지 않는다.
