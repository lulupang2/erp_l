# ADR-0003: SvelteKit + TypeScript와 Go API의 책임 분리

- 상태: 채택 / 구현 전
- 기록일: 2026-09-11
- 출처: Svelte는 사용자 지정, SvelteKit + TypeScript는 기존 계획에 포함된 진행 합의 구성
- 관련 요구사항: PRD FR-01~07, NFR-04, 9절

## 배경

사용자는 Svelte 프론트엔드를 원한다. MVP에는 여러 업무 화면과 입력 폼, 목록·상세 간 이동이 필요하다.
생산과 재고의 최종 판정은 Go API에서 일관되게 수행해야 한다.

## 결정

SvelteKit + TypeScript로 화면을 구성하고 Go API가 업무 규칙과 DB 접근을 소유한다.
프론트엔드는 입력 보조와 예상 소비량을 표시하되 서버 검증을 대체하지 않는다.
DB에 직접 연결하거나 SvelteKit 서버에 생산·재고 로직을 중복 구현하지 않는다.
화면은 같은 출처의 /api를 사용하고 로컬 프록시가 Fiber로 전달한다.

## 대안

| 대안 | 판단 |
| --- | --- |
| Svelte만 사용하고 라우팅 등을 별도 구성 | 가능하지만 현재는 SvelteKit 구성으로 진행하기로 했다. 비교 구현은 하지 않았다. |
| React 또는 Vue | 사용자 지정 Svelte를 따른다. 우열을 검증한 결과가 아니다. |
| SvelteKit 서버에서 업무 API까지 처리 | Go 백엔드라는 기술 제약과 맞지 않는다. |

## 결과와 단점

UI와 업무 API의 책임을 구분하고 응답 타입·명세를 기준으로 통신한다.
Go와 TypeScript 두 도구 체계를 관리해야 하며 서버·화면 타입을 자동으로 동일하다고 가정할 수 없다.
서버와 화면에서 입력 검증을 일부 중복하되 최종 권위는 서버에 둔다.
정적 출력·SSR·배포 어댑터는 공개 배포 시 별도 선택한다. 이 ADR 작성 당시에는 공개 배포 방식을 확정하지 않았다.
후속 사용자 배포 요청으로 production 어댑터는 [ADR-0008](0008-rocky-linux-cicd.md)에서 `adapter-node`로 결정했다.

## 검증과 재검토 조건

핵심 시연, 로딩·빈 목록·저장 실패, 성공 후 재조회와 타입 검사를 확인한다.
배포 환경이나 렌더링 요구가 구체화되면 해당 방식만 별도 결정한다.
