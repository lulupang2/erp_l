# 조립 제조 ERP — PRD

문서 버전: 0.3  
작성일: 2026-09-11  
상태: 기존 합의에 기반한 제품 요구사항 / 구현 진행 중. 실제 검증 상태는 [PROGRESS](PROGRESS.md)에서 관리한다.

## 1. 목적과 문서 관계

이 문서는 누구를 위해 무엇을 만들며, 어떤 결과가 나오면 MVP를 완료한 것으로 판단할지를 정의한다.
제품 목표, 기능 범위, 핵심 업무 정책과 제품 인수 조건은 이 문서를 기준으로 관리한다.
구현 방법은 [SSOT의 상세 설계](SSOT.md)에서 관리하고, 기술 선택 이유는 [ADR 목록](adr/README.md)에서 관리한다.

SSOT는 별도의 문서 종류라기보다 항목마다 신뢰할 기준을 하나로 유지한다는 원칙이다.
이 프로젝트에서는 PRD가 제품 요구사항의 기준이며, SSOT.md는 문서별 책임 안내와 상세 설계를 담당한다.
기술 설계가 제품 범위를 바꾸어야 한다면 먼저 PRD를 변경한다.

## 2. 배경과 해결할 문제

조립 제조 과정에서는 부품 재고, 제품별 자재 구성, 생산 계획과 실적을 연결해서 확인해야 한다.
이 값들을 따로 관리하면 부분 생산이나 불량이 발생했을 때 남은 생산량과 실제 재고를 일치시키기 어렵다.

이 프로젝트는 해당 흐름을 작은 서비스로 구현해 풀스택 개발 역량을 보여주는 포트폴리오다.
실제 업체 인터뷰나 운영 데이터로 검증된 사업 요구사항은 아니며, 현재 시나리오는 대화에서 정한 데모용 제품 가정이다.

## 3. 대상 사용자와 사용 환경

| 대상 | 목적 |
| --- | --- |
| 제조 업무 담당자 역할의 데모 사용자 | 부품·BOM을 등록하고 생산 실적과 재고를 관리한다. |
| 포트폴리오 평가자 | 하나의 업무가 화면부터 데이터 처리까지 연결되는지 확인한다. |
| 개발자 | 재현 가능한 시나리오로 정합성을 검증하고 후속 기능을 확장한다. |

- 한국어 데스크톱 브라우저에서 사용한다.
- 하나의 조직과 재고 위치를 가정한다. 로그인과 역할별 권한은 제공하지 않는다.
- MVP 인수는 로컬 실행과 Neon 연결을 기준으로 완료했다. 후속 사용자 요청으로 Rocky Linux의 `erp.jisung.lol` 포트폴리오 배포를 추가하되, 애플리케이션 계정 기능을 추가하지 않고 reverse proxy 인증으로 접근을 보호한다.

## 4. 목표와 성공 기준

1. 부품 입고 → BOM 정의 → 생산 지시 → 부분 생산·불량 등록 → 재고 확인을 화면에서 끝까지 수행할 수 있다.
2. 생산 결과와 자재 소비가 일치하며, 실패·중복 제출·동시 처리로 수량이 틀어지지 않는다.
3. 평가자가 예제 데이터와 안내 문서로 동일한 결과를 재현할 수 있다.

성공 여부는 아래 인수 조건의 통과로 평가한다. 실제 사용자 수나 매출, 근거 없는 처리량·응답 시간 목표는 두지 않는다.

## 5. MVP 요구사항

아래 요구사항은 모두 MVP 필수다. ID는 후속 설계·테스트에서 추적에 사용한다.

| ID | 사용자 요구 | 제품 인수 조건 |
| --- | --- | --- |
| FR-01 | 부품과 완제품을 구분해 관리하고 싶다. | 코드·이름·종류·단위로 품목을 등록하고 목록·상세에서 확인한다. 코드는 중복되지 않는다. |
| FR-02 | 제품 하나에 필요한 부품 구성을 정의하고 싶다. | 완제품에 하나 이상의 부품과 정수 소요량을 등록·교체한다. 중복 부품과 완제품을 자재로 넣는 요청은 거절한다. |
| FR-03 | 부품을 입고하고 수량을 확인하고 싶다. | 양수 정수 수량으로 입고하고 현재고 증가와 입고 이력을 확인한다. |
| FR-04 | 제품과 수량으로 생산 계획을 만들고 싶다. | BOM이 있는 완제품의 지시를 만들고 계획·양품·불량·잔여·상태를 조회한다. |
| FR-05 | 여러 차례 생산한 양품과 불량을 기록하고 싶다. | 부분 실적을 반복 등록하고 계획 범위 안에서 누적 수량과 상태가 갱신된다. |
| FR-06 | 생산에 따른 재고 변화를 자동으로 반영하고 싶다. | 처리 수량만큼 자재가 소비되고 양품만 입고된다. 자재 부족 시 실적과 재고 모두 변경되지 않는다. |
| FR-07 | 재고가 왜 변했는지 확인하고 싶다. | 품목별 현재고와 변동 이력을 조회하고 원인 입고·실적을 확인한다. |
| FR-08 | 같은 데모를 다시 실행하고 싶다. | 예제 데이터와 안내를 제공하고 전용 데모 데이터를 초기화할 수 있다. |

### MVP에서 제외하는 기능

구매·발주, 판매·출고, 회계, 다중 회사·창고, 로트·유통기한, 다단계 BOM,
자재 예약·선투입, 재공품, 재작업·자재 회수, 생산 취소, 입고·실적 수정·삭제,
사용자 계정·권한, 공개 배포를 MVP 기능에서는 제외한다. 별도 대시보드도 필수 요건이 아니다.

2026-09-11 후속 요청으로 공개 인터넷에서 접근 가능한 **보호된 포트폴리오 배포 환경**은 MVP 이후 전달 범위에 추가했다. 이는 사용자 계정/권한 기능을 구현한다는 뜻이 아니며, 인증 없는 업무 API 공개를 허용하지 않는다.

품목 수정·삭제는 최소 범위를 위한 현재 초안의 기본값으로 제외한다.
후속 기능 목록은 확정된 개발 일정이나 구현 약속을 의미하지 않는다.

## 6. 핵심 업무 정책

| ID | 정책 |
| --- | --- |
| BR-01 | 계획 수량은 양품 목표가 아니라 양품+불량의 처리 목표다. 잔여는 계획에서 누적 처리 수량을 뺀 값이다. |
| BR-02 | 실적 등록 시 양품+불량 수량에 해당하는 BOM 자재를 차감하고, 양품만 완제품 재고로 추가한다. |
| BR-03 | 불량은 자재를 전량 소비한 것으로 처리하며 회수·재작업하지 않는다. 부족한 양품을 보충하려면 새 지시를 만든다. |
| BR-04 | 실적은 양품·불량 각각 0 이상의 정수이고 합계는 1 이상이어야 한다. 잔여 수량을 초과할 수 없다. |
| BR-05 | 누적 처리량 0은 대기, 계획 미만은 진행 중, 계획과 같으면 완료다. 완료 지시에 새로운 실적은 추가하지 않는다. |
| BR-06 | 재고를 예약하지 않는다. 지시는 재고 부족 상태에서도 만들 수 있으나 실적은 소비할 자재가 충분할 때만 등록된다. |
| BR-07 | 기존 생산 지시는 생성 당시 BOM을 유지한다. BOM 변경은 이후 생성한 지시에 적용한다. |
| BR-08 | 수량은 정수만 지원하며 단위 환산은 하지 않는다. 신규 품목의 현재고는 0이다. |

양품 0·불량만 있는 실적도 유효하다. 이 경우 자재만 소비하며 완제품 재고는 증가하지 않는다.
입고·계획·BOM 소요량은 양수여야 한다. 구체적인 필드 길이와 수량 상한은 상세 설계의 입력 제한이다.

## 7. 대표 사용자 여정과 시연 결과

1. 케이스·스위치를 부품으로, 키보드를 완제품으로 등록한다.
2. 케이스 10개와 스위치 800개를 입고한다.
3. 키보드 1개당 케이스 1개·스위치 80개인 BOM을 등록한다.
4. 키보드 10개 생산 지시를 생성한다.
5. 1차 실적으로 양품 4개·불량 1개를 등록한다.
6. 2차 실적으로 양품 3개·불량 2개를 등록한다.
7. 생산 지시와 재고 이력에서 결과를 확인한다.

## 8. 품질 및 실패 처리 요구사항

| ID | 요구사항 | 인수 조건 |
| --- | --- | --- |
| NFR-01 | 데이터 정합성 | 재고가 음수가 되지 않고, 현재고는 변동 이력 합계와 일치한다. 지시 집계는 실적 합계와 일치한다. |
| NFR-02 | 원자적 처리 | 자재 부족이나 처리 중 오류에서 실적·집계·재고가 일부만 저장되지 않는다. |
| NFR-03 | 중복·동시 요청 | 같은 작업 재전송이 중복 반영되지 않고, 경쟁 요청이 계획이나 가용 재고를 초과하지 않는다. |
| NFR-04 | 상태 안내 | 로딩·빈 목록·실패를 표시하고 저장 실패 시 입력을 유지한다. 부족 자재와 필요·현재 수량을 알려준다. |
| NFR-05 | 접속 정보 관리 | DB 비밀값을 브라우저나 저장소에 노출하지 않는다. DB 연결 실패 시 성공으로 표시하지 않는다. |
| NFR-06 | 재현 가능성 | 실행 안내와 예제 데이터가 있고, 자동 통합 테스트는 실제 Neon 접속 정보 없이 실행 가능하다. |

## 9. 기술 제약과 문서 작성 순서

기존 대화에서 확정된 기술 제약은 Go Fiber, SvelteKit + TypeScript, Neon PostgreSQL,
sqlc + pgx(ORM 미사용), 모노레포와 모듈형 모놀리스다.
이 제약의 구체적인 적용 방법은 SSOT에서 정의하고, 선택 배경·대안·단점은 ADR에서 기록한다.

진행 순서는 PRD 정리 → ADR과 상세 설계 정합성 정리 → 구현 → 검증이다.
2026-09-11 후속 요청으로 코드 구현을 시작했고 로컬 PostgreSQL과 실제 Neon 검증을 분리했다. 이후 사용자가 Rocky Linux 서버와 `erp.jisung.lol` 도메인 배포를 요청해, 기존 업무 기능을 바꾸지 않는 보호된 포트폴리오 배포/CI-CD를 후속 범위로 추가했다.

## 10. MVP 완료 조건

- FR-01~08과 BR-01~08, NFR-01~06을 충족한다.
- 7절의 시연을 재현하고 표와 동일한 결과를 확인한다.
- 자재 부족, 초과 생산, 전량 불량, 중복 제출, 동시 생산, BOM 변경 시나리오를 검증한다.
- 실행 방법·예제 데이터·시연 절차·검증 결과를 제공한다.

제품 인수 조건의 기준은 이 문서이며, 기술 테스트 방법은 [SSOT 10절](SSOT.md#10-검증과-완료-기준)을 따른다.
