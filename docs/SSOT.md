# 조립 제조 ERP — SSOT v2

문서 버전: 2.0 초안  
작성일: 2026-09-12  
상태: v2 목표 설계 / 전체 구현 진행 중, 실제 완료·검증 대기

## 1. 문서 책임과 버전

[PRD](PRD.md)의 F2/B2 요구를 구현하는 목표 설계다.
보존된 v1 코드·데이터의 기준은 [SSOT-V1](SSOT-V1.md), [PRD-V1](PRD-V1.md), [v1 ERD](ERD.md)다. 병렬 작성 중인 v2 코드·DDL·계약을 이 문서만으로 구현 완료로 판정하지 않는다.
전환은 [FACTORY-PLAN](FACTORY-PLAN.md)의 전체 단계로 수행한다. 최종 통합 담당자가 실제 계약·마이그레이션·실행 결과를 [PROGRESS](PROGRESS.md)에 기록하기 전에는 v2 검증 대기 상태다.
[ADR-0009](adr/0009-factory-production-flow.md)는 v1 대비 변경 배경을 관리한다.

## 2. 업무 경계와 모델

단일 Go API와 PostgreSQL을 유지한다. 인증·기준정보·생산·자재·품질 모듈을 구분하고 서비스 계층이 전표 확정을 조정한다.

| 영역 | 목표 데이터와 책임 |
| --- | --- |
| 인증·감사 | 사용자, 역할, 세션, 전표 작성·확정·정정·목표 변경 이력 |
| 기준정보 | 품목, 논리 위치, 부품 로트, 불량 사유, 승인 BOM 개정, 승인 검사 기준 |
| 지시 | 목표, 허용 착수 수량, 고정 BOM/검사 기준, 담당자, 상태, 변경 승인 이력 |
| 작업 | 지시별 작업 세션, 시작/종료, 신규 산출 보고, 실제 소비 로트 배분 |
| 재고 | 품목·로트·위치·지시 소유 구분의 잔액, 다행 수불 문서와 증감 원장 |
| 품질 | 산출 로트, 부분 검사, 항목 결과, 합격·부적합 수량, 처분, 재작업과 재검사 |
| 완제품 입고 | 합격 산출분 참조와 부분 입고량, 중복 입고 잔량 검증 |
| 정정 | 원전표 참조 역분개, 사유, 승인자, 후속 문서 의존관계 |

BOM과 검사 기준은 초안·승인·사용 중지로 관리하며 승인 후 수정은 새 개정으로 한다.
지시는 발행 시 해당 개정과 필요한 이름·단위·소요량을 고정한다. 실제 소비량은 별도 저장한다.
로트 추적은 실제 소비 로트를 생산 보고와 연결하는 수준이며 개별 제품 일련번호 추적은 제공하지 않는다.
동일 생산 보고 내 혼합 투입은 해당 산출 로트 전체에 연관된 것으로 기록한다.

## 3. 재고·산출물 수량

부품 재고 버킷은 창고 가용과 지시별 현장 미소비로 나눈다. 소비·폐기는 출고 원장으로 남긴다.
조립 산출물은 검사대기 → 합격대기 또는 부적합 → 입고/재작업/폐기 흐름으로 관리한다.
부품 소비와 조립품 산출은 단위가 다르므로 수량 자체를 서로 더하지 않는다.

- 지시 현장 잔액 = 불출 - 반납 - 실제 소비 - 현장 자재 폐기 (각 정정 반영).
- 로트 신규 산출 = 미검사 + 합격 미입고 + 순입고 + 부적합 보류 + 재작업 중 + 조립품 폐기.
- 재검사 대상은 재작업 중에서 미검사로 이동한다. 신규 산출 합계는 증가하지 않는다.
- 입고 잔량 = 해당 합격분 - 이미 입고한 수량 (역분개 반영).
- 목표 잔여 = max(목표 - 순입고, 0). 초과 입고는 목표 변경 승인 전까지 거절한다.
- 정상 마감: 순입고가 목표에 도달하고 미해결 산출·작업·현장 자재가 모두 0.
- 조기종결: 목표 미달 사유·권한 확인과 동일한 정리 조건 적용.

검사 합격 수량이 목표를 초과하더라도 검사 결과를 거짓으로 제한하지 않는다.
초과분은 합격대기에 남기고 생산관리의 사유 있는 목표 증가 승인 후 입고한다. 합격품 임의 폐기·불량 전환은 승인된 처분 기능이 아니므로 구현하지 않는다. 별도 처분이 필요하면 PRD 정책 결정이 선행되어야 한다.
이 상태에서 마감은 거절한다.

### 3.1 수량 한도와 계산 기본값

[v1 수량 규칙](SSOT-V1.md#3-용어와-수량-규칙)의 정수·안전 상한을 보수적으로 이어받되, v1의 양품+불량 목표 의미는 이어받지 않는다.

| 대상 | v2 구현 기본값 |
| --- | --- |
| 목표·허용 착수 총량·신규 산출 총량 | 목표/허용 착수는 1~1,000,000, 누계 신규 산출은 0~허용 착수. 목표 변경·추가 승인 후 총량도 상한 이내 |
| BOM 단위 소요량·부품 입고 한 행 | 1~1,000,000 |
| 불출·반납·실제 소비·자재 손실의 같은 품목 합계 | 1~1,000,000,000,000, 대상 가용 잔량 이하. BOM 1,000,000 × 산출 1,000,000을 표현할 수 있게 재고 상한을 사용하며 여러 로트/중복 버킷 행은 합산 검증 |
| 생산 보고·검사·처분·재작업·완제품 입고 수량 | 명령 총량 1~1,000,000, 원천 잔량 이하. 검사 합격/부적합은 각각 0 이상이며 합계가 검사량과 일치 |
| BOM 차이의 0소비·무자재 재작업 | 사유를 갖춘 0소비/빈 소비 내역 허용; 0수량 원장 행은 만들지 않음 |
| 품목 재고·각 로트/위치/지시 버킷 잔액 | 0~1,000,000,000,000; 같은 품목의 창고+현장 합계도 이 상한 유지. 내부 이동으로 상한을 우회하지 않음 |

소수·음수 입력·비정수 표현은 거절한다. Go int64 / PostgreSQL BIGINT / JSON 정수를 사용하며 곱셈·덧셈 전 overflow와 업무 상한을 검사한다. 여러 로트 배분·동시 명령·역분개에도 합계와 잔량 검증을 같은 트랜잭션에서 수행한다.
누적 원장 합계 계산은 최종 잔액만 작다고 안전하다고 가정하지 않는다. 이 기본값으로 표현 불가능한 수량이 필요하면 제한을 임의 확대하지 말고 PRD/계약 결정 후 변경한다.

## 4. 전표 확정과 정정

전표 초안은 수정할 수 있고 재고에 영향이 없다. 확정은 불변 전표·원장·집계·감사 기록을 한 트랜잭션에서 저장한다.
주요 전표는 부품 입고, 불출, 반납, 자재 폐기, 생산 보고, 검사, 부적합 처분, 재작업 보고, 완제품 입고다.

생산 보고는 산출 수량과 BOM 제안 대비 실제 소비 내역을 함께 제출한다.
새 조립의 BOM 자재별 소비 차이 또는 0소비는 차이 사유를 요구하고, 지시 마감에서 생산관리가 확인한다.
재작업은 추가 소비만 입력한다. 단순 조정 작업은 추가 자재 0을 허용한다.
산출 없는 현장 손실은 생산 보고에 억지로 넣지 않고 자재 폐기 전표를 사용한다.

검사는 검사대기 로트의 일부를 잠그고 합격/부적합으로 분리한다.
합격 수량에는 해당 검사 기준의 필수 항목 결과가 있어야 한다.
부적합에는 사유를 요구하며 재검사는 원검사와 재작업 지시를 참조한다.

정정은 사유와 관리자 승인을 요구한다. 후속 사용분이 있으면 취소를 거절하고 후속 전표부터 되돌린다.
재고를 음수로 만드는 역분개도 거절한다. 역분개는 DB migration down이나 직접 UPDATE가 아니다.
서버 기록 시각과 사용자가 입력한 실제 작업 시각을 구분하고 과거일 입력으로 원장 순서를 재작성하지 않는다.

## 5. 권한과 동시성

개별 계정·서버 세션과 역할 권한을 구현한다. 사용자 ID를 요청 본문으로 신뢰하지 않는다.
관리자가 계정을 발급하며 자가 가입은 없다. 비밀번호 해시와 HttpOnly 세션 쿠키를 사용하고 권한은 서버에서 검사한다.
상태 변경에는 같은 출처 검사와 CSRF 방어를 적용한다. 구체적인 암호화 라이브러리는 구현 시 검증한다.

reverse proxy Basic Auth는 사용하지 않는다. v1 익명 업무 접근은 이 v2 인증 설계로 소급 보호되지 않으며, v2 세션·권한은 서버 구현과 거절 시나리오로 별도 증명한다.
로그인 세션은 서버가 발급하고 현재 활성 계정/역할을 매 요청 확인한다. 로그아웃·만료·계정 비활성화 후에는 재사용을 거절한다. 쿠키 Secure(production)·HttpOnly·SameSite 및 CSRF/출처 검사를 계약에 고정한다.
작업 세션은 로그인 세션과 별도 업무 리소스다. 서버가 실제 사용자·배정 지시·수행 역할을 연결하고 다른 작업자의 진행 세션으로 생산/재작업 보고를 확정하지 못하게 한다. 로그인 만료·로그아웃만으로 진행 작업을 자동 종료하거나 산출 처리하지 않는다.

모든 확정·취소·발행·보류/재개·승인·작업 시작/종료·마감 명령에 요청 식별자를 적용한다.
요청 키의 고유 범위는 **서버가 확인한 사용자 계정 ID + 작업 종류 + UUID 키**다. 로그인 세션 ID에 묶지 않아 같은 계정의 재로그인 후 불확실한 성공을 재확인할 수 있다. 다른 계정은 원요청 결과를 재생하거나 소유권을 넘겨받지 않는다.
요청 해시에는 대상 경로 ID·정규화 입력·명령 의미를 포함한다. 재응답도 현재 계정·역할·대상 접근 권한을 먼저 검사하며, 권한 철회 후 저장된 성공 결과를 노출하지 않는다. 같은 키/다른 입력은 충돌, 같은 키/동일 입력은 기존 결과다. 같은 문서의 확정·입고 잔량 제약은 다른 계정/키에도 중복 확정을 막는다.
성공 키는 업무 변경과 함께 저장하고 세션 만료로 삭제하지 않는다. 실패한 트랜잭션은 키도 롤백하며, 첫 v2에서는 성공 키 자동 만료를 도입하지 않는다. 브라우저 재시도 상태도 계정별로 격리하고 계정 전환 시 다른 사용자의 저장 요청을 자동 제출하지 않는다.
오래 열린 초안은 버전 필드로 수정 충돌을 검출한다. 초안 소유권·작업 배정 변경·관리자 정정 권한은 FACTORY-PLAN의 명령별 인수표와 함께 API에 고정한다.

잠금 순서는 요청 키 → 관련 작업 지시 ID 순 → 생산/검사/처분 원문서 ID 순 → 재고 버킷 키 순으로 통일한다.
재고 버킷 키는 품목·로트·위치·지시 소유자를 포함한다. 신규 버킷은 고유 제약과 upsert 후 잠금으로 처리한다.
원장·잔액·품질 수량·전표 상태·감사 기록을 동일 트랜잭션으로 확정하고 실패 시 전체 롤백한다.
교착/재시도 가능한 실패는 기존 요청 키로 재확인한다. DB 작업 중 외부 서비스를 호출하지 않는다.

## 6. 인터페이스 변경

v1 결과 API에 새 의미를 덮어쓰지 않는다. 새 흐름은 /api/v2 계약으로 추가하고 화면도 버전 경로를 구분한다.
이 저장소의 v1 ERD와 DTO 설명은 v1 의미를 보존한다. v2 DDL·OpenAPI·생성 코드·서버·화면은 전체 구현 작업에서 함께 작성·대조하며 최종 검증 상태를 PROGRESS에 기록한다.

| 인터페이스 영역 | 필요한 명령/조회 |
| --- | --- |
| 계정 | 로그인·로그아웃·현재 사용자·관리자 계정/역할 관리 |
| 기준정보 | 위치·로트·BOM/검사 기준 개정 및 승인 |
| 작업 지시 | 초안 저장·발행·보류·재개·추가 착수 승인·목표 변경·마감·조기종결 |
| 자재 전표 | 입고·불출·반납·손실 초안/확정/역분개 |
| 작업 세션·보고 | 시작·종료, 산출+실제 소비 보고 확정 |
| 품질 | 검사 확정·부적합 처분·재작업 생성/보고·재검사 |
| 완제품 입고 | 합격분 조회·부분 입고 확정/역분개 |
| 대조·감사 | 위치/로트 재고·지시 수불·산출 상태·문서 연결·작업자 기록 |

API 상태·오류 코드는 단계별 OpenAPI에 고정한다. 완료 이전에는 v1 테스트에 v2 성공을 표시하지 않는다.

## 7. 전환과 검증 원칙

v2는 별도 PostgreSQL schema와 DB 역할을 사용해 v1 데이터 접근을 분리한다. 실제 DDL/권한 적용 여부는 통합 담당자의 실행 증거로 확인하며 문서 작성만으로 생성되었다고 주장하지 않는다.
v1 미완료 지시를 v2 목표 수량으로 자동 전환하지 않는다. v1에서 마감하거나 해당 범위의 전표를 정리한다.
이전 데이터에 없는 로트·검사·작업자를 추정해 만들지 않는다.
기초 재고 전환은 실사·전환 기준 시각·담당자 승인과 원천 대조를 갖춘 별도 절차로 한다.
v2 적용 대상의 v1 쓰기를 동결한 뒤 전환하며 구버전 API는 이 범위에서 읽기만 허용한다.

격리된 로컬 검증부터 진행한다. Neon이나 운영 DB의 리셋·파괴적 변경은 계획에 포함하지 않는다. 공개 배포에서 proxy 인증을 사용하지 않으므로 v1 익명 조회·쓰기 위험과 v2 앱 권한 검증을 별개로 기록한다.
기존 리뷰 지적은 후속 결정·수정·검증 증거별로 추적한다. Basic Auth 복구 요구는 no-proxy-auth 결정으로 대체되며 다른 배포 지적이나 문서 정합화를 자동 해결 처리하지 않는다.
인수 시나리오와 단계별 완료 조건은 FACTORY-PLAN을 따른다.
