### 검증된 업무 및 장애 시나리오

실제 UI에서 케이스 10·스위치 800을 입고하고 BOM 1/80, 계획 10의 지시를 생성했다. 1차 양품 4·불량 1에서 현재고 5/400/4·잔여 5, 2차 양품 3·불량 2에서 현재고 0/0/7·누계 7/3·잔여 0·완료를 확인했다.

전량 불량은 자재만 소비하고 완제품 변동을 생성하지 않는다. 재고 부족·계획 초과·현재고 상한은 기록 일부만 남기지 않고 거절한다. 같은 지시 경쟁과 공통 자재 경쟁에서도 계획 초과·음수 재고가 발생하지 않음을 검증했다.

동시 같은 키의 입고·지시·실적은 한 번만 생성하며 성공 재요청은 같은 리소스를 반환한다. 다른 입력이나 다른 지시 경로에 같은 실적 키를 쓰면 거절한다. 실패한 요청 키는 남지 않고 재시도할 수 있다.

DB 통합 테스트에서 실적 삽입 후, 자재 차감 후, 누계 갱신 후 등 중간 단계에 실패를 주입하고 10개 업무 테이블의 전체 상태가 되돌아가는지 비교했다. 입고·품목·BOM·지시 생성의 실패도 원자적 롤백을 확인했다. BOM 교체와 새 지시 생성의 경쟁에서 서로 다른 리비전이 섞이지 않고 이전 복사본이 보존되는 것을 확인했다.

브라우저에서 실제 서버 저장 직후 응답만 유실시키고 새로고침한 뒤 같은 키·본문으로 재확인했다. 입고는 1건만 남고, 이미 완료 상태가 된 생산 지시도 기존 실적 재확인이 가능했다. 조회 오류 표시 테스트의 503은 브라우저에 의도적으로 주입했으며 실제 Neon 장애 복구 검증이 아니다.

최종 실제 화면 스크린샷 `.local/ui-order-completed.png`, `.local/ui-receipt.png`를 육안 확인했다. 페이지당 표시 수가 빈 값으로 보이던 문제를 수정하고 20/50건 선택 동작을 브라우저 테스트에 포함했다.

## 환경 조치와 해결한 문제

브리지 PATH에서 Node가 발견되지 않아 공식 Node 26.8.2를 `.tools`에 SHA-256 검증 후 구성했다. 사용자 시스템 Node나 전역 PATH는 변경하지 않았다. 설치된 Go 1.21.4 런처에서 Go 1.26.7 도구 체계를 사용하며 pnpm은 10.11.0이다.

sqlc의 Go 소스 빌드는 Windows C 링커 오류로 실패했다. 공식 sqlc 1.31.1 Windows 실행 파일의 SHA-256과 버전을 검증해 사용했고, 실제 코드 생성·재생성 비교를 통과했다. 최초 timestamptz 타입 매핑 오류는 sqlc 설정을 수정한 뒤 재생성해 해결했다. 생성 파일을 직접 수정하지 않았다.

Docker 엔진 연결을 복구하고 ERP 전용 PostgreSQL 17.10 두 인스턴스를 구성했다. 기존 다른 프로젝트 컨테이너 설정은 변경하지 않았다. 비밀값은 추적 제외 `.env`에만 생성하고 웹 도구 환경에서는 제거한다.

빌드의 adapter-auto는 공개 배포 대상을 감지하지 못했다는 안내를 출력하지만 빌드 자체는 성공했다. 공개 배포 어댑터 구성은 이번 범위가 아니다. 실행 환경의 NO_COLOR/FORCE_COLOR 안내는 테스트 실패가 아니다.

## 남은 작업과 미검증 범위

**실제 Neon 체크리스트는 완료**했다. [NEON-CHECKLIST](NEON-CHECKLIST.md)의 메이저 버전 일치, 실제 verify-full TLS, 마이그레이션, 생산 처리, 실제 유휴 전환 후 첫 요청과 접속 실패 거절/복구를 확인했다. 실제 관측과 테스트 단위의 한정된 결과이며 모든 네트워크 장애나 미래 동작을 보장하는 것은 아니다.

브라우저는 사용자 Windows의 Chromium에서 검증했다. Firefox/WebKit, 공개 배포 환경, Go race detector는 이번에 실행하지 않았다. Goose down 경로는 대상 제한을 구현했지만 실제 down/up 왕복 검증은 수행하지 않았다. MVP 범위 밖 기능을 임의로 추가하지 않았다.

## 후속 연결 작업 이력

### 후속 설정 확인 (2026-09-11)

후속 요청에서 실제 환경 설정을 비밀값 출력 없이 확인했다. `DATABASE_URL`, `MIGRATION_DATABASE_URL`, `TEST_DATABASE_URL`은 모두 로컬 PostgreSQL을 가리키며 `.env`는 Git 추적 제외 상태다. 원격 Neon 연결 정보는 현재 실행 환경에 설정되어 있지 않다.

Neon 연동 연결을 안내했다. 연결 후 ERP 전용 프로젝트/DB를 확인하는 것이 다음 시작 지점이며, 새 외부 리소스 생성이 필요하면 별도 확인한다. 이번 후속 점검에서 원격 연결·마이그레이션·데이터 쓰기나 전체 테스트 재실행은 하지 않았다. 실제 Neon 검증은 계속 미완료다.

### Neon 연동 후 대상 확인 (2026-09-11)

사용자가 Neon 연동을 연결한 뒤 계정·조직의 프로젝트 목록, 브랜치와 DB 메타데이터 조회에 성공했다. 접근 가능한 조직의 프로젝트 목록에서도 `ji` 프로젝트 하나만 확인했고, `main` 브랜치와 `neondb`, `dev`, `cms` DB가 조회되었다. ERP 전용으로 식별되는 프로젝트나 DB는 확인되지 않았다.

기존 프로젝트·브랜치·DB는 변경하지 않았다. 접속 비밀값 조회, 애플리케이션 환경 변경, 원격 SQL 실행, 마이그레이션과 생산 데이터 쓰기는 수행하지 않았다. 연동을 통한 메타데이터 조회 성공은 Go 애플리케이션의 직접 TLS 연결 검증과 구분한다.

다음 시작 지점은 ERP 전용 `assembly-erp` 프로젝트 신규 생성에 대한 사용자 확인이다. 승인 후 사용 가능한 리전과 로컬 테스트 DB에 맞는 PostgreSQL 17 구성을 확인하고 전용 대상으로 실제 연결·마이그레이션·업무 흐름을 검증한다. 실제 Neon 검증 체크리스트는 계속 미완료로 유지한다.

### 승인된 Neon 리소스 생성과 검증 시작 (2026-09-11)

- 신규 프로젝트: `assembly-erp` / `square-pond-46750950`, 브랜치 `main` / `br-aged-poetry-b32szyik`, DB `erp_demo`.
- 계정에서 조회한 리전 중 한국과 가까운 싱가포르(`aws-ap-southeast-1`)를 사용했다. PostgreSQL 17, 컴퓨트 최소/최대 0.25 CU로 생성했고 기존 `ji` 프로젝트는 변경하지 않았다.
- suspend interval을 명시한 첫 생성 요청은 계정 정책으로 거절되었다. 프로젝트가 생성되지 않았음을 목록에서 확인한 후 해당 옵션을 생략해 한 번 생성했다. 유휴 설정은 계정 기본값을 유지한다.
- 원래 `.env`와 로컬 데모/테스트 DB는 보존하고, Git에서 제외된 `.env.neon`에만 직접 연결과 `verify-full` 설정을 저장했다. 일반 테스트/초기화 명령은 여전히 로컬 전용이다.
- 실제 `pnpm neon:migrate` 실행으로 Goose 스키마 버전 1 적용을 확인했다. 이어서 실제 브라우저 시나리오와 유휴 복귀를 아래와 같이 검증했다.

### 실제 유휴 재개 증거와 도구 제한

2026-09-11 12:16:03 UTC 이후 API 프로세스(PID 35276)를 그대로 유지하고 쿼리를 중단했다. Neon 제어 API에서 해당 endpoint의 상태가 `idle`, `suspended_at=2026-09-11T12:21:17Z`인 것을 관측했다. 수동 suspend 명령이나 keep-alive SQL은 보내지 않았다.

12:22:25 UTC의 첫 재고 요청은 HTTP 200으로 1,617ms에 완료했다. 같은 API PID가 요청 전후 살아 있는지 확인했고 응답 SHA-256은 대기 전 값과 동일했다. 이후 읽기 전용 진단에서 TLS 인증서 검증, Goose v1, 집계 불일치 0을 재확인했으며 PostgreSQL 시작 시각도 12:22:25 UTC로 변경되었다.

원래 실행 세션의 stdin이 닫혀 있어 유휴 관측 메시지를 직접 입력할 수 없었다. API를 재시작하지 않고 별도 제어 명령으로 동일 프로세스에 최초 조회와 대조를 수행했다. 성공 증거를 저장한 뒤 대기하던 제어 프로세스와 그 API만 종료했다. 이 관리상 종료로 원래 `pnpm neon:verify` 세션은 exit 1이었으므로 그 명령 자체를 무인 전체 실행 통과로 표시하지 않는다. **실제 DB·브라우저·유휴 재개 검증 결과는 통과**이며 최종 보고서의 `resume_controller`에 인계 사실을 기록했다.

후속으로 `.local/neon-idle-observation.json` 파일 입력도 지원하도록 보완했다. 닫힌 stdin, 오래된/다른 endpoint/미래 관측 거절, 증거 없는 시간 초과를 포함한 테스트 4개가 추가되어 스크립트 테스트 총 11개가 통과했다. 파일 입력 수정 후 전체 클라우드 시나리오를 한 명령으로 다시 실행하지는 않았다. 이미 검증한 DB를 반복 변경하거나 유휴 대기를 중복 실행하지 않았다.

최종 근거는 `.local/neon-verification.json`, `.local/neon-resume-verification.json`, `.local/neon-idle-observation.json`, `.local/neon-browser-results.json`, `.local/neon-dev-smoke.json`이다. 로컬 시드의 CASE/KEYBOARD/SWITCH 재고 10/0/800도 별도 조회로 보존을 확인했다. 기존 `ji` 리소스, 공개 배포, 커밋·푸시는 변경하지 않았다.
